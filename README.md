# Credit Risk Classification

An end-to-end machine learning project for **credit approval decisions** on the
[German Credit Dataset](https://archive.ics.uci.edu/dataset/144/statlog+german+credit+data).
The system trains four complementary models, combines them in a weighted
ensemble, tracks experiments with MLflow, exports deployable inference
artifacts, and serves predictions through a Streamlit app.

**Hosted demo:** [Try here](https://credit-risk-h6wzqyepauzgpp29kypx9e.streamlit.app)

---

## Overview

This repository is built around a practical lending problem: how to make better
approval decisions when the cost of a bad approval is much higher than the cost
of a missed good customer. At the same time, the dataset is small and rather imbalanced, which requires careful feature engineering and modeling strategies.

The project includes:

- raw data processing and train/test preparation
- a reproducible pipeline: train → select on validation → score once on test → export
- custom feature engineering
- model-specific preprocessing pipelines
- Bayesian hyperparameter search
- cost-sensitive threshold optimization on a held-out validation set
- weighted ensemble scoring
- MLflow experiment tracking and registry integration
- exported pickle pipelines for app inference
- a Streamlit application for interactive prediction
- Docker support and automated tests

## Dataset and Target Semantics

The German Credit Dataset contains **1,000 applicants** and **20 features**.

This project uses an explicit target definition that is important to understand:

| Encoded class | Meaning |
| --- | --- |
| `1` | Good credit / low risk |
| `0` | Bad credit / high risk |

That is the reverse of many common credit-risk conventions, where `1` often
means default or bad risk. In this repository:

```text
P(class = 1) = probability of good credit
```

The Streamlit app also shows:

```text
Default risk = 1 - P(class = 1)
```

## The Ensemble

The final ensemble combines four trained models:

| Key | Model | Weight |
| --- | --- | ---: |
| `lrc` | Logistic Regression | 1.0 |
| `rfc` | Random Forest | 2.5 |
| `svc` | Support Vector Classifier | 2.0 |
| `cat` | CatBoost | 1.0 |

Ensemble probability:

```text
P_ensemble(class = 1) =
(1.0 * P_lrc + 2.5 * P_rfc + 2.0 * P_svc + 1.0 * P_cat) / 6.5
```

Decision rule:

- if `P(class = 1) >= 0.66` → **Low Risk**
- otherwise → **High Risk**

`model_config.yml` is the source of truth for the weights and threshold; the app and
scoring scripts read them from there.

### How the ensemble was selected

The weights and threshold are chosen on a **validation set**, never on the test set. A grid of
256 weight combinations is swept on 150 validation rows, the top 15 are shortlisted by ROC AUC,
and each shortlisted candidate then has its decision threshold tuned to minimise expected cost.
The lowest-cost candidate is promoted and scored **once** against the hold-out test set.

Model fitting optimises ranking quality, and the cost matrix only comes in when the operating
point is chosen. `scripts/select_ensemble.py` writes the result straight into `model_config.yml`,
so the shipped configuration is generated by the script and re-running it reproduces the same
values. The full procedure is in [`docs/instructions.md`](docs/instructions.md) §7, and
[`notebooks/investigation.ipynb`](notebooks/investigation.ipynb) section 8 runs the same search
interactively, with the diagnostics and plots.

## Results

Test set: 159 applicants (106 good, 53 bad), scored once with the shipped configuration.

| Policy | Total cost | Notes |
| --- | ---: | --- |
| Approve everyone | 265 | Pays the 5x penalty on all 53 bad applicants |
| Reject everyone | 106 | The floor any model has to beat |
| Best individual model (SVC) | 75 | At its own validation-tuned threshold |
| **Weighted ensemble** | **76** | Shipped configuration |

The ensemble is effectively tied with the best single model (76 vs 75). It is retained
because it is more stable across the validation candidates than any individual model, but
this dataset does not demonstrate an ensemble advantage.

Ensemble metrics at the operating threshold:

| Metric | Value |
| --- | ---: |
| ROC AUC | 0.823 |
| Precision | 0.903 |
| Recall | 0.613 |
| Accuracy | 0.698 |
| F1 | 0.730 |
| Brier score | 0.162 |

### How much of this is noise

Bootstrapping the test set (5,000 resamples) puts the ensemble's cost at **76, 95% CI
[51, 104]**, an interval roughly eleven bad approvals wide. Its advantage over rejecting
everyone is **30.1, 95% CI [-2, 58]**, which only just fails to exclude zero
(P(better) = 96.6%).

So the ensemble is probably better than the trivial policy, but 159 test rows cannot
establish it at 95% confidence, and any comparison between configurations differing by
less than about 40 cost units is reading noise. That is a limit of the dataset (1,000 rows
with a 15% test split) rather than the pipeline. A cost figure quoted without an interval
would invite more confidence than 159 rows support.

### Operating point

| Measure | Value |
| --- | ---: |
| Applicants approved | 45.3% (72 of 159) |
| Good applicants approved | 61.3% (65 of 106) |
| Good applicants turned away | 38.7% (41 of 106) |
| Bad applicants approved | 13.2% (7 of 53) |

A 5:1 cost ratio buys precision by refusing business. This configuration turns away 41
creditworthy applicants to avoid 46 bad loans. Whether that trade is worth making depends
on the margin per good loan against the loss given default. The 5:1 ratio comes from the
UCI documentation.

Note on accuracy: approving every applicant scores 66.7% accuracy on this class balance,
so accuracy near that number is expected at a cost-optimal threshold. Cost is the headline
metric for that reason.

## Cost-Sensitive Objective

The project is tuned for an asymmetric cost structure:

| Error Type | Meaning | Cost |
| --- | --- | ---: |
| False Positive | Approve a bad borrower | 5 |
| False Negative | Reject a good borrower | 1 |

The cost matrix is used in one place only: choosing the decision threshold on the
validation set. Model fitting optimises ROC AUC, so the models are selected for ranking
quality and the cost asymmetry sets the operating point.

## Modeling Approach

The ensemble mixes four learning styles: Logistic Regression for a linear baseline, Random
Forest for nonlinear interactions, SVC for margin-based separation, and CatBoost for boosted
trees with native categorical handling. Each model gets its own preprocessing path and its own
imbalance strategy rather than a single shared pipeline.

The feature engineering, the per-model encoder choices, and the reasoning behind them are
covered in the project write-up and in
[`notebooks/feature_engineering.ipynb`](notebooks/feature_engineering.ipynb).

## Streamlit App

The app takes a random applicant from the dataset or a manually entered one, and returns the
ensemble probability, a per-model breakdown, the explicit **Good Credit Probability** and
**Default Risk**, and the final **Low Risk / High Risk** verdict at the production threshold.

Export the trained pipelines to `app/models/` before launching it locally.

---

## Running it

```bash
uv sync --extra dev --extra app
uv run python scripts/process_data.py && uv run python scripts/split_data.py
uv run python main.py                              # train four models
uv run python scripts/select_ensemble.py --write   # choose weights + threshold on validation
uv run python scripts/score_ensemble.py            # score once, on test
uv run python scripts/export_pipelines.py          # .pkl artifacts for the app
uv run streamlit run app/streamlit_app.py
```

Requires Python `>= 3.13` and [`uv`](https://docs.astral.sh/uv/). Docker is optional.

Installation options, configuration reference, the training and selection workflow, Docker
deployment, CI, and testing are all covered in
[`docs/instructions.md`](docs/instructions.md).
